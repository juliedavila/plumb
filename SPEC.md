# Plumb 0.6.0 specification

Plumb holds a complex system as designed against the system as built, for systems built over time: a local-first checked model with executable rule packs, proposals with impact reports, a capability-based plan, current state kept as discovered or confirmed, and generated views.

**0.4 contract:** compose designs over a shared root, review organization decisions and retain the lone-instance behavior. The author can build an instance, open one local HTML file, follow the plan, see the checks fail and pass, propose a patch and see its impact, and ask an agent questions about the plan through MCP. It runs on fictional examples and independently released designs.

The 0.5 contract adds an Obsidian vault as generated output. Human annotations return through notes.yaml as proposals. The model and its accepted decisions remain the source of truth.

## Hard constraints

- bun and TypeScript only. No npm dependencies at all (YAML via `Bun.YAML.parse`, tests via `bun test`). Never python.
- Each design page is one self-contained HTML file: plain HTML, CSS and vanilla JavaScript, with the bundle inlined as JSON, no CDN, no fonts from the network, no library, opens from `file://`. Diagrams are SVG laid out by our own code.
- Generated pages and examples use fictional names and role titles. Keep identifying details out. The external scrub list is read from `PLUMB_SCRUB_LIST`, else `~/.config/plumb/scrub.txt`.
- Keep local working data out of distributables. Verify frozen design inputs before importing.

## Layout

```
plumb/
  plumb.ts                  CLI: designs, roots, portfolios, tracker, editions, migrations, packaging
  src/types.ts           the shared contract in code
  src/core/              load, compile (apply patches), rules runner, plan analysis, impact, bundle
  src/site/              site generator: bundle -> one HTML file
  src/mcp/               MCP stdio server over a built bundle
  packs/<name>/index.ts  rule packs: export const pack: RulePack
  instances/<name>/      an instance (layout below)
  tests/                 bun test
```

## Plumb edition interface 1

A released design supplies `edition.yaml` with `line`, `namespace`, exact string `version`, `released: true`, date, build, schema, shared and manual_work references, pins, files and digest. Interface 1 adds:

```yaml
line: intake
namespace: intake
version: "1.0.0"
released: true
date: "2026-10-28"
build: fictional-1
schema: { design_engine: "0.4" }
plumb:
  interface: 1
  engine: plumb/engine.yaml
  model: plumb/model.yaml
  plan: plumb/plan.yaml
```

This fictional repair-intake release is generated with a complete stamp by `bun tests/fixtures/make-editions.ts`. The three interface files, shared seams and optional separate manual-work catalog must appear in `files: [{ path, sha256 }]`. `shared` and `manual_work` each carry the same path/hash as their file entry; an absent catalog is explicitly `manual_work: null`. The digest is SHA-256 over `<sha256>  <path>\n` in the manifest's listed order. Pins carry namespace, version and the full SHA-256 of the other design's edition.yaml. A design's own build supplies these inputs; Plumb performs no design-specific translation.

Engine-format model files declare `teams: []`. Every owned element or unit has the role string in both `owner` and `owner_as_written` (the latter may be in attrs), never a team id. A fictional example is `{ id: desk, name: Intake desk, kind: service, owner: "counter operations", owner_as_written: "counter operations" }`. At addition time, the workspace root's team map resolves these roles; Plumb retains their wording in record attributes. Optional org.yaml holds teams once; without it the map declares teams and each design receives the registry. Security rules classify arbitrary contracts using `attrs.evidence_content`, `attrs.proof_condition` and `attrs.nonpublic_context`, or design `security.evidence_contracts`, `proof_contracts` and `context_contracts` lists. Classifications are namespaced during composition.

```sh
plumb design add <namespace>@<version> --from <folder | github:<owner>/<repo>> [--workspace <dir>] [--with-pins] [--ref <git ref>] [--path <path in repo>]
```

Workspace defaults to the current directory. Local lookup tries the supplied folder, `<folder>/<namespace>/<version>`, then `<folder>/editions/<namespace>/<version>`. Recursive local pins can also be found as sibling editions when the supplied source was a direct edition folder. GitHub uses `https://raw.githubusercontent.com/<owner>/<repo>/<ref>/<path>/`: default ref `<namespace>-v<version>`, default path `editions/<namespace>/<version>`. An explicit ref also applies to pins; a path override selects the requested edition, and pins use their default edition paths. `PLUMB_GITHUB_RAW` changes the raw base URL for a local mirror. Deprecated `DE_*` settings print a one-line notice when used.

The source first supplies edition.yaml, followed by exactly its listed files. Plumb stages them in a temporary folder. Every file is capped at 32 MB, and the edition including its stamp at 256 MB. Redirects are followed only within the same origin, with a finite redirect limit and request timeout. Namespaces and versions must be safe design identifiers. File paths must be canonical, unique, portable relative paths; traversal, absolute paths, symlinks, overlapping file/directory paths and manifest/adapter-sidecar collisions are refused.

All verification and derivation finish before workspace writes:

1. Parse the stamp; require requested namespace and line, exact version, released true and interface 1.
2. Verify every listed SHA-256 and the digest. Interface and shared inputs must be listed, with matching hashes. Unlisted source files are never read or used.
3. Compare shared seams and manual-work bytes against every edition involved and the existing root. Refuse disagreements with a filename and the design provenance that brought the existing layer. A new root has kind root, schema 0.4 and shared_from provenance, without a fabricated team map.
4. Verify each pin's exact version and full stamp hash. An installed design at a different version or hash is refused. Missing pins print an exact addition command; with `--with-pins`, verify and add dependencies first from the same source. Follow installed transitive pins too and refuse cycles and conflicting requirements.
5. Refuse a changed stamp under an existing version. Re-add an identical stamp to apply a changed team map and re-derive adapters. Validate destination paths and maps before committing.

Copy published bytes to `instances/<namespace>/editions/<version>/` and the live edition.yaml unchanged. Write derived live engine.yaml, model.yaml and plan.yaml. Frozen engine adapters sit beside the published inputs with an `engine-import.yaml` sidecar bound to the original stamp and adapter hashes. They normally use engine.yaml, model.engine.yaml and plan.engine.yaml; choose non-conflicting adapter names when a release already lists one of those paths. Building a released edition verifies and reads those adapters while using live state from the instance folder.

Create empty notes.yaml only when absent. Preserve existing progress, milestones, current state, notes, tracker, reports, deck, tour and patches. The shared root's shared_from.editions records every added design's namespace, version and stamp hash. Unresolved owners remain role text; merge them into a sorted `instances/shared/team-map.draft.yaml` with `owners: { role: { teams: [] } }`, never replacing team-map.yaml. Print each design's resolved and unresolved role counts and the draft path. Suggest portfolio build only when a portfolio exists, otherwise build the added instance.

## Instance layout

```
instances/<name>/
  engine.yaml     name, title, description, packs: [generic, ...], ladder (fidelity levels, default [none, stand-in, existing-tool, built]), glossary (optional, below)
  model.yaml      teams, systems, zones, elements, relationships, contracts, views
  plan.yaml       phases, units
  patches/*.yaml  one patch per file
  tour.yaml       optional: the presentation tour (title, steps of target, title, say, highlight). The build warns on a gone target and on a caption that contradicts a computed verdict or status
  notes.yaml      optional: notes and questions pinned to records (below)
  diffs/*.json    optional: compared builds saved by `plumb diff --save`
  deck.yaml       optional: the present-mode deck (below)
  milestones.yaml optional: milestone words, dates and overrides beside a generated plan (below)
  progress.yaml   optional: unit status set by a person, beside the plan (below)
  reports/*.json  optional: report snapshots saved by `plumb report`
```

Model records (all ids unique within their kind. unknown keys go in `attrs`, which packs may read):

- `teams[]`: `id`, `name`, `description?`, `lead?` (who runs the team: one free string, a person's name in a real deployment and a role title in the shipped instances. see Leads)
- `systems[]`: `id`, `name`, `description?`
- `zones[]`: `id`, `name`, `description?` (trust or organizational boundary. packs decide meaning)
- `elements[]`: `id`, `name`, `kind` (free string, e.g. service, store, person, process, queue, ui, external-system), `system?`, `zone?`, `owner?` (team id), `verifier?` (team id), `parent?` (element id), `description?`, `attrs?`
- `relationships[]`: `id`, `from`, `to`, `kind` (free string, e.g. data, control, feedback, handoff), `label?`, `carries?` (contract names), `optional?`, `attrs?`
- `contracts[]`: `name`, `description?`, `produced_by?`, `consumed_by?` (element ids), `attrs?`
- `views[]`: `id`, `title`, `elements` (ids), `relationships?` (ids. default: all among the elements)
- `claims[]` (additive): `id`, `statement`, `kind` (premise | claim | assumption. default premise), `grade` (evidence | inference | judgment | untested. default untested), `source?`, `fallback?`, `rests_on?` (claim ids), `attrs?` (e.g. `tested_by`: the units that test it). Elements, relationships, units, phases and claims may carry `rests_on: [claim ids]`. A patch may add, modify or remove a `claim` like any other record.

Plan records:

- `phases[]` (shown as milestones): `id`, `name`, `exit_test` (a sentence a person can check), `order` (number), `delivers?` (the value it delivers, one sentence), `means?` (what reaching it lets the organization do or claim), `target?` (ISO date), `accountable?` (a role: who decides), `confirmed_by?` (a role: who confirms the status independently), `lead?` (who owns delivering its outcome, apart from who decides its status. see Leads), `override?` (`status`: red | amber | green, `reason`, `date`, `by`, `review_by?` (YYYY-MM-DD)). `<instance>/milestones.yaml` (`milestones: { <phase id>: { delivers, means, target, accountable, confirmed_by, lead, override } }`) sets the same fields over a generated plan. A phase id the plan lacks is a build warning. An override that is not a mapping, has no status of red, amber or green, no reason, no `date` (YYYY-MM-DD) or no `by` is a `core/override-valid` error at the milestone and is not applied. `<instance>/progress.yaml` (`units: { <unit id>: { status, date, by, reason? } }`) sets a unit's status over the plan's and copies the entry to the unit's `attrs.status_set`. An entry with no status of todo, doing or done, no date or no `by` is a `core/progress-valid` error at the unit and is not applied, and an unknown unit id is a build warning. An entry may name the unit's `lead`. An entry with a lead and nothing else sets only the lead and needs no date or `by`. Unlike the milestone fields, a unit's status moves the model hash, as it does in plan.yaml. These fields, a unit's `due`, every `lead` (a team's, a milestone's, a unit's), and engine.yaml's `status:`, `tracker:`, `importer:` and `glossary:` keys are left out of `engine.modelHash`. `bun plumb.ts build` prints its first twelve characters as `model:`.
- `units[]`: `id`, `title`, `kind` (code | agreement | measurement | free string), `phase` (phase id), `elements?` (`[{id, from, to}]` fidelity moves on the ladder), `requires?` and `provides?` (capability ids), `check` (the done-condition), `owner?` and `verifier?` (team ids. only where they differ from the parts the unit moves, see Teams and roles), `feedback?` (minutes | next-run | several-runs | weeks), `status?` (todo | doing | done. default todo), `due?` (ISO date), `lead?` (who drives it, over its owner team's lead. see Leads), `attrs?`

Patch file: a mapping with `id`, `title`, `status` (proposed | accepted | rejected, any case), `why`, `ops[]`, and optionally `provenance` (`author`: `agent`, `person` or a person's role, never a name. `agent: {tool, model?}`, `requested_by` (a role), `request`, `created`, `based_on`: the `engine.modelHash` prefix it was written against. The change review leads with "Proposed by": an agent at `requested_by`'s request, or the person, by `author`'s role or, for `author: person`, by `requested_by`) and `decision` (`by`, `at`, `reason`). A file that does not parse, is not a mapping, has an unknown status, or whose `ops` is not a list is a `core/patch-loads` error at that file (the patch is skipped or applies nothing) and the build still writes its outputs. two files with one id are a `core/patch-ids-unique` error, and each file keeps its own impact. Design ops: `add` / `modify` / `remove` on `element | relationship | contract | team | system | zone | unit | phase | view | claim`:
- `{op: add, kind: element, value: {...}}`
- `{op: modify, kind: element, id: X, set: {...}}` (shallow merge. `attrs` merged one level. A missing or non-mapping `set` is an op error and changes nothing)
- `{op: remove, kind: element, id: X}` (removing an element also removes relationships touching it and its ids from contracts, views and unit element lists. The impact report lists that cascade)

Every YAML file of an instance is scanned for a key written twice in one mapping (the parser keeps the second without a word): each is a `core/yaml-keys-unique` error naming the file and line (src/core/yaml-keys.ts).

Compile = the base model and plan plus every **accepted** patch, applied in natural id order. `impact <patch>` compiles with and without that one patch (any status) and diffs. A finding that disappears because the record it sits on was removed is reported as gone with the record, not resolved. A record removed outright is listed under removed only, not again under cascade. Units affected also include units that move an element at either end of a relationship the patch's ops add or remove. A unit the cascade leaves with none of the parts it moved is a `core/unit-keeps-a-part` error (in the patch's impact, and in the build for an accepted patch). Each impact carries a `verdict` (`PatchVerdict`): `fail` when it introduces an error finding. `caution` (shown amber, never green) when findings leave only with a removed record, when its title or why names a unit that is not done (a precondition not met), or when they name a part (by its name of two words or more), a contract (its name split at capitals) or an id that no op touches (a contract is backed only by an op on it or a relationship carrying it, never by a cascade). Else `pass`. It holds the reasons in words, a reject line (the file and `status: rejected`, with `decision`) and a revise line (the file, or what to tell Claude).

## 0.4 current state and shared-root decisions

- `CUR-disposition`: a missing disposition in `current.yaml` is undecided. `core/current-valid` reports a warning while the record is discovered and an error once a person has confirmed it. A refused confirmation leaves it discovered. The Today block and record card show the gap. No disposition is inferred, so an undecided record drives neither retirement checks nor transition classification. Unknown dispositions and malformed records remain errors.
- `CUR-shared`: a design records current state only for its own parts, including its today-only parts. Bare and namespaced references to shared parts, and references to another design's parts, are errors. A replacement may still be a shared part. Shared parts' current state has no home in 0.4.
- `CUR-dates`: retirement ordering inside a design uses milestone order. across designs it uses target dates. If either target date is absent, order is unknown and no ordering finding is raised. The separate warning for a retirement that does not depend on its replacement's arrival still applies in the composition.
- `ROOT-contracts`: every crossing held in the shared layer, including crossings on organization-added seams, needs a contract or a non-empty string `no_contract` explaining why none is needed. Write the reason on the crossing or in `attrs`. The loader keeps it in `attrs.no_contract`. `shared/crossing-valid` rejects a missing, blank or non-string reason when no contract is carried. A reason leaves security marks, never-cross restrictions and contract resolution checks in force.
- `ROOT-floor`: floors come from the shipped checks. A patch that rewrites a floor, even to add relevance, is refused by `shared/mark-valid` and the computed floor stays unchanged. To add relevance, use `security.raised: { by, why }`. clearing a shipped floor never lowers a mark.
- `ROOT-rowowner`: an explicitly written team's `row_owner` stays in the root's model hash, so changing it makes pending patches refer to an older root. When absent, the org view defaults the row owner to the lead without adding that default to the fingerprint. The lead itself and estimate notes remain wording, outside the model hash.

## Rule packs

A pack is `packs/<name>/index.ts` exporting `pack: RulePack` (types in `src/types.ts`). A rule reads the compiled model and plan and returns findings. Severity `error` fails `plumb check` (exit 1). `warning` reports. Shipped packs:

- `generic`: referential integrity (every id reference resolves), every element has an owner team, free text (notes, claim statements, sources and fallbacks, patch reasons) names no email address or @handle (warning. The message says where, never what), contracts have a producer and consumer, every relationship that carries a contract connects a producer to a consumer of it, views name existing ids.
- `plan`: every required capability is provided, no dependency cycles, every phase has an exit test, a unit's fidelity moves follow the ladder upward, unit owner exists, a unit in an earlier phase does not depend on one only provided later, a unit does not require a capability only it provides, a done unit's required capabilities are provided by done units. When two units share an id, plan analysis uses the first in file order.
- `flow` (value streams): every handoff relationship between two teams is counted. warn when a path from a start to an end element crosses more than N team handoffs (N from `engine.yaml` `flow.max_handoffs`, default 4), naming the path's hops ("Product to Design, …"). every `queue` element declares `attrs.wip_limit`. every person-step declares `attrs.wait_days` so lead time can be summed. `flow-values`: every `wait_days`, `work_days` and `wip_limit` is a number of at least zero (a WIP limit whole), with `flow_source` (measured | estimated | declared) and `flow_as_of` (a date) on the part or as engine.yaml `flow.source` / `flow.as_of`, no older than `flow.max_age_days` (default 90) at the build date (`RuleContext.today`), and a process step in a stream view declares its wait.
- `plan/done-unit-holds`: a done unit whose `attrs.asserts` (`[{ every: <part kind>, has: <attribute or field>, in?: <view> }]`) the model contradicts (warning).
- `security`: checks inference boundaries, evidence integrity, partitioning, independent verification and control feedback over the model.
- `premises` (run whenever the model declares claims, listed or not): every `rests_on` names a declared claim (error). every claim has a statement, a known kind and grade (error). no cycle of claims (error). And "load-bearing and untested": a premise or assumption graded untested on which at least N records rest (warning. N from `engine.yaml` `premises.load_bearing`, default 5. The weight counts every dependent record with the plan slice in place of the units).
- `tracker` (run whenever the instance has a `tracker/` folder, listed or not, so a generated engine.yaml still gets it): the reconciliation's categories as findings (see Tracker).
- `notes` (run whenever `notes.yaml` exists): a note whose target no longer exists is orphaned (warning, `atKind: note`). Notes on findings (`pack/rule@at`) are checked after every other rule has run.

## Flow (src/core/flow.ts, src/tracker/flow.ts, src/core/flow-layout.ts)

Stream views: engine.yaml `flow.streams`, else every view whose drawn relationships include a handoff. `bundle.flow` (`FlowFacts`, only with the flow pack and a stream view): `elements` (each part's declared `wait`, `work`, `wip` as `FlowValue` with source, date, age and staleness, and `measured`), `streams` (`StreamFlow`: the path with the most handoffs from a start to an end, ties by length. `wait` and `work` as sums by source with the steps missing one. `lead` and `efficiency` only when work is declared at every step with a wait. `handoffs`, `limit`, `hops` in path order, each with the step whose wait follows it. `oldest`, `sources`. `measured`: the tracker's lead time, the steps it covers and their declared wait and work), `teamHandoffs` (every handoff relationship between two owner teams, per pair) and `measured` (`FlowMeasured`). tracker/mapping.yaml `flow: { statuses: { <status>: { step, as: wait | work } }, done: [...] }` (done defaults to the statuses the status map maps to done). `TrackerIssue.transitions` come from Jira's changelog. medians are over completed stays, open stays are counted apart. lead time runs from the first mapped status to the first done status after it. Without a flow mapping or status history, `measured.available` is false with the reason. Each patch impact carries `flow` (`PatchFlowEffect` per stream it changes: wait before and after, removed and added by source, lead time, handoffs before and after with the limit, hops added and removed, steps removed with what the tracker measured there, and the sentence). A stream view's layout is replaced by `streamLayout`: the path left to right in rows (`ViewLayout.stream`), parts off the path in a lane under the step they connect to, every other line orthogonal through the gaps so no line crosses a box. A phase may carry `flow_target: { lead_days, handoffs }` (left out of the model hash). The deck's road shows `DeckMilestone.flow` for it.

## Glossary

`bundle.glossary` (`GlossaryTerm[]`, src/core/glossary.ts): the engine's generic terms (`ENGINE_GLOSSARY`: part, relationship, zone, view, contract, unit, capability, milestone, definition of done (the milestone's "Reached when". forms exit test, reached when), critical path, can start now, path to green, owner team, lead, premise, claim, rationale (the claims a record rests on), grade, load-bearing, rule, finding (forms problem, problems), patch, verdict, override (forms manual status, set manually), tracker, note, hand-off, lead time, WIP limit, fidelity, focus), merged with engine.yaml `glossary: { <term>: <definition> | { definition, forms } }`: an entry named like an engine term (any case) replaces its definition (and its forms when given), a new name adds a term, and an entry with no definition is a build warning and skipped. `forms` are the words that match on the page (default: the term and its plural). A design may supply its own terms through the instance config. The site (client/glossary.js) marks each term's first use in the tour caption (per step) and in the visible h2 and h3 headings of the page shown (per page. Never a screen-reader-only heading, a link, a chip or an id) with a focusable dotted underline whose definition shows on hover or focus, in one tooltip (`role=tooltip`, `aria-describedby` while shown) that Escape, blur or leaving closes.

## Reader text

`Finding.text` (additive, src/core/reader.ts): a finding's message with every record id it names replaced by the record's name (a unit's title, a milestone's name, a claim's statement cut near 80 characters, a part's name, a relationship as "A → B", a patch's title), where the token looks like an id or a kind word stands before it, and attribute keys in words ("WIP limit", "partition key"). Absent when the message names no id. Rule keys and finding keys stay as written.

Rendered prose, capability filters and briefs use declared names. A capability without a declared name falls back to its key as plain words with the namespace removed. Older imported titles with a namespace and capability prefix receive reader wording without rewriting frozen inputs or their hashes. Namespaced ids remain available in links, data attributes and code formatting.

## Premises: "if this is false"

A record rests on a claim when its `rests_on` names it. `premiseImpact` (src/core/premise.ts) is computed like a patch impact: the direct dependents. every record resting on the claim directly or through other claims (breadth first, each with the chain of claims that reaches it). counts by kind. And the plan slice, every unit that rests on it directly, moves a part that rests on it, or sits in a milestone that rests on it, grouped by milestone in plan order, with how many are not done. The bundle carries one per claim in `bundle.premises`, with `exposure` (`PremiseExposure`): the units that test it (`attrs.tested_by`, those in the plan), the milestone where its first test lands (the earliest one holding a test), and `before`, the open units of its plan slice in milestones before that one (every open unit of the slice when nothing tests it). `rankByStakes` orders the Strategy page: grade (untested, judgment, inference, evidence), then `before`, then milestones at stake, then weight. `bun plumb.ts premise <instance> [id]` prints it (or every claim ranked by weight) as Markdown, and the MCP `premise` tool returns the same text.

## Notes

`notes.yaml` is `notes: [{ id, target: { kind, id }, kind, text, status, answer?, answered_by?, sources?, author, created, updated }]` (`sources`: a list of strings, the commands and files an answer was read from, shown under the answer. An answer written on the page drops them. `answered_by`: person or agent. The page shows an agent's answer as "Answered by Claude", a page answer is recorded as a person's, and a missing one says who answered is not recorded) with target kinds element, relationship, contract, unit, phase, claim, patch and finding. The engine loads it into `bundle.notes` (`{ version, items }`, open questions first. `version` is a hash of the file's bytes). Bad notes are build warnings, never errors. Notes come only from this file, written by people, by agents and by the page under the dev server. Nothing is pulled from a tracker, chat or any other tool, and the Notes page says so in one line (`NOTES_SOURCE`, src/site/strategy.ts). The dev server serves `GET` and `POST /__de/notes` (src/dev/notes-api.ts): a write needs this run's token (`X-DE-Token`, injected only into the page the server sends), a Host of `127.0.0.1:<port>` or `localhost:<port>`, an Origin of exactly that server, a same-origin `Sec-Fetch-Site` when sent, JSON of at most 64 KB with only the fields its op allows (`add`, `edit`, `answer`, `resolve`, `reopen`, `delete`), a target that exists in the last good build, and the `version` of the file as it is now. A stale version is a 409 with the current version. The write edits only the changed note's lines (comments and order stay), goes to a temporary file in the instance directory and is renamed over `notes.yaml`. The watcher then rebuilds and the page reloads. The dev loop also compares every watched file's time and size each half second, so an in-place edit the file watcher misses (BSD `sed -i`) still rebuilds. It never rebuilds for `reports/`. `plumb dev` takes `--out` and refuses an instance outside the repository without it. The request code lives in the dev server's snippet, so the offline file holds no network code.

## Comparing builds

`src/site/client/digest.js` (loaded by the page and by `src/core/diff.ts`) reduces a bundle to one short hash per part, relationship, unit, claim, finding, patch and note, with each one's state (a unit's done, doing, ready or blocked. A patch's status. A note's status. A claim's grade), and compares two digests into a `BuildDiff` (types.ts). Parts, relationships and units carry `~` and a four-character hash of the record without its name, title, label, description, owner, verifier and status, so a record whose only change is its wording or owner is `reworded` (counted apart in `counts[kind].reworded`), not changed. `DIGEST.churnText` says "Titles and owners were re-derived (by the importer, version a to b). The design did not change" when nothing else in the design changed, and a status move whose new side is an override carries `override` and `computed` ("went amber to green by override. Computed still amber", `DIGEST.moveText`). Findings new and gone, units newly ready or done, records added, removed and changed, notes added, answered and resolved, patches added and decided, claims regraded, and counts by kind. The page keeps the digest of the last build its reader saw in `localStorage` and leads the Overview with "Since you last looked". `bun plumb.ts diff <instance> --from <a> [--to <b>]` compares two builds, each a bundle file or the instance at a git ref. The other side defaults to the instance now. `--save` writes the comparison to `<instance>/diffs/`, and the Changes page shows saved comparisons.

## Teams and roles

The model's `teams` are the registry. `elements[].owner` and `elements[].verifier` name declared teams. So may `units[].owner` and `units[].verifier`. `unitRoles` (src/core/teams.ts) gives each unit its owners and verifiers: the distinct teams of the parts it moves (in registry order), or its own value. The source is `parts`, `override` (it names a team that differs from its parts), `declared` (it moves no part with one) or `none`. `teamFacts` adds the unowned parts, the unassigned units by milestone (with how many are open), the waits-on map (team A waits on team B for every dependency of an open A unit on a B unit, A ≠ B, with the unit pairs), the load (open units each team owns and its share), the role-by-milestone counts (`byGate`, a data key), and separation of duties at team level. A part is judged when it names an owner and a verifier: it fails when the verifier is its owner (`owner`), one of its co-owners in `attrs.owner_teams` (`co-owner`) or one of the teams in `attrs.not`, the teams it must stay independent of (`excluded`). An owner team in `attrs.not` fails it too, judged or not (`excluded-owner`). A part that names no verifier is not assessed, never passed (`checkedParts`, `passedParts`, `failedParts`, `notAssessedParts`). Unit role pairs in `attrs.<pairs_attr>` (default `separates`) are checked where both roles map to teams: through `role_map` to owner, verifier or decider (default proposer and owner to owner, verifier to verifier. The decider is the union of the unit's parts' `attrs.decider`, a team id or a list), or through `role_teams` to the team that holds the role. A pair falls to one team when the two sides share one. Counts of the pairs checked, unmapped and still waiting on a team. The load counts owners only: co-owners and teams named only in `attrs.owner_roles` add nothing. The bundle carries it as `bundle.teams` (`TeamFacts`). engine.yaml settings: `teams: { max_share: 0.4, role_map: {...}, role_teams: {...}, pairs_attr: separates }`.

The `teams` pack (added whenever the model declares teams): `verifier-team-exists` (error. also a part's decider, excluded and co-owner teams), `unit-has-owner` (warning per open unit with no owner team. The page lists the current milestone's and gives the others as counts by milestone), `team-load` (warning per team owning more than `max_share` of the open units, from five open units up) and `separation-of-duties` (warning. titled as a team-level proxy. The Teams page says how many parts were judged, passed and failed, and how many were not assessed). Owners that name no declared team stay errors of `generic/references-resolve` (parts) and `plan/unit-owner-exists` (units). The tracker's reconciliation compares each linked unit's owners with the team the mapping reads off its issue (`TrackerReconcile.ownerDisagreements`, only when the mapping has `owner_team`). `tracker/owner-agrees` reports each disagreement. Likely matches and the CSV export use the inherited owners too.

## Leads

An optional `lead` at three levels, one free string each: a team's (who runs it, `teams[].lead`. Imported leads pass through from the team map), a milestone's (who owns delivering its outcome, `phases[].lead` or milestones.yaml) and a unit's (who drives that piece of work, `units[].lead` or progress.yaml). In this repository a lead is a fictional name or role title. Real names go in only in a real deployment. `unitLeads` (src/core/teams.ts) gives each unit its lead as `bundle.leads.units` (`UnitLead`): `set`, its own. Else `team`, its owner team's lead, from the first of its owner teams in `unitRoles` order, with `of` counting them when there are several. Else `none`. A missing lead is never a finding and no rule reads it (an owner field counted as a target gets filled for the count): where a lead would show, the page says "No lead named". The page shows a team's lead in its card (hover included) and the Teams page's table and team work line. A milestone's on its card, its status block and the road (not the Overview's compact road). A unit's in its card's first context row and its page's Teams section, marked "set on this unit" or "inherited from <team>, its owner team" ("the first of its N owner teams" where it has several). In present mode the milestones slide names each milestone's lead under its name (`DeckMilestone.leadName`. A name or role, never an id), and the status slide's notes say "led by <lead>" or "no lead named" per milestone. Leads are left out of the model hash, and a comparison counts a lead change as wording (`lead` is among the digest's words, and a unit's and a milestone's lead are compared by value). The tracker's assignee is not read: the Jira adapter maps no assignee field, and adding one is not in this pass.

## Report snapshots

`bun plumb.ts report <instance> [--presented]` (src/core/snapshot.ts, report-cli.ts) builds the instance and writes `reports/<UTC time with dashes>.json` (never over another file. A second in the same second gets `-2`): `ReportSnapshot` in types.ts, which is the digest of src/site/client/digest.js plus phase status, findings by rule, the tracker's counts and newest change, the premise summary, the ownership gap, each milestone's status and computed status and the plan's (`status`), the engine version and the rule set's version (`rules`, a hash of every pack, rule and severity. also `engine.rules` in the bundle). The digest itself carries the status (`s`) and the rule keys (`rk`), so a comparison (`BuildDiff.status`, `.checks`) lists status moves milestone by milestone and keeps findings of rules one side lacks apart from the design's (changes in the checks). A snapshot also records `importer` (engine.yaml `importer:`, which an importer writes with its own adapter and title versions). `plumb report` writes one snapshot per build hash: the same build again writes nothing and says which file holds it, and `--presented` marks that file. `presented` is set by `--presented` or by the dev server's `POST /__de/report` (`{ "op": "present" }`, the notes API's Host, Origin, Sec-Fetch-Site and token checks. ## Status

src/core/status.ts computes `bundle.status` (`PlanStatus` in types.ts) after the teams, premises and tracker: per milestone in plan order `{ phase, status, computed, reached, current, reasons[], override?, path[] }`, the plan `overall` (worst shown status, worst computed, one sentence), `challenges` (at most five: slipped, unprovided and error work one each, unowned work, tracker disagreements and the heaviest untested belief one each, idle ready work. red first) and `risks` (`RiskBet` per load-bearing untested premise: `bet`, `ifWrong`, `testing`). engine.yaml `status: { red: [...], amber: [...] }` names the criteria (defaults: red no-provider, unowned-blocker, error-finding, slipped. amber unowned, untested-premise, tracker-disagrees, idle-ready, earlier-milestone). A criterion in both is red. An unknown one is a warning. A milestone's path: its open units and their transitive dependencies, leaving out units in an earlier unreached milestone. Due dates compare as calendar days against `engine.built`. Claims behind a milestone: its `rests_on`, its units' and the parts they move, each with the claims those rest on. A reached milestone is green. An override sets `status` and leaves `computed`. The path is computed whenever `computed` is not green. "Earlier milestone" uses the computed status, never an override: an earlier milestone not reached whose computed status is not green keeps a later one at least amber, as "Its work waits on X" where the later one's path depends on its work, else as "It can be reached only after X" (the nearest such). A red reason whose first record is a unit with a tracker status disagreement ends "(Jira says In Review. settle first)", in its text and its short line. `MilestoneStatus.flags` (`OverrideFlag`): on an override, `upstream-red` (green while an earlier unreached milestone is computed red), `worsened` (computed worse now than in the last report saved on or before the override's date) and `review-due` (`review_by` before the build day). `accountable` and `confirmed_by` are copied from the phase. With `confirmed_by` the card reads "Status set by: <accountable> · Confirmed by: <confirmed_by>", else "Accountable: <accountable>". The card, the road (`DeckMilestone.flags`), the deck's road, `plumb brief` and the milestone card's "Set a status by hand" disclosure show them. A path step with no owner reads "Needs an owner: <accountable> names one". `bundle.history` (`StatusHistory`, src/core/snapshot.ts `statusHistory`): a column per distinct report snapshot (`uniqueReports`: one per build hash, the presented one first), oldest first, then this build unless the newest report is this build. per column each milestone's status, computed status, done and total, the plan's status and the count of load-bearing untested premises, `recorded: false` for a snapshot with no status. The Plan draws it as "Status over time". Each reason carries `short`, its one line. `overall.lead` is the one status sentence ("Overall red. “X” is blocked: <its first reason's short line>") that the Overview's brief opens with, the Plan's status line and the deck's road lead with, and the milestone's card repeats. A path on a slide cut short at its limit ends with "This is not the whole path: N more steps are on the Plan" (`DeckItem.more`). A milestone's untested-premise steps name the heaviest beliefs first, as its reason, the challenges and the risks do. Each claim's `PremiseImpact.atStake` is the milestones not reached whose own work (the milestone's or its units' `rests_on`, through other claims, never through a part) rests on it. `PremiseImpact.amberBy` is the milestones whose status reasons name it as untested ("turned amber by this", which also counts a part their work changes). The Strategy row, the claim page and `plumb premise` show the two apart, and a red milestone is never said to be red because of an untested belief.

## Present mode

## Plan analysis (in the bundle)

- capability graph: unit A depends on B when A requires a capability B provides.
- `layers`: pull layers (topological levels) over units not done. `frontier`: units whose dependencies are all done (startable now). `blocked`: for each other unit, which capabilities are missing and which units would provide them.
- `critical_path`: longest dependency chain (by unit count), ties broken by natural id order.
- per phase: units total / done, and whether every unit is done.

## Tracker (additive)

The model owns structure (units, phases, dependencies). The tracker owns live state (status, assignee, sprint). Each kind of disagreement (status, a dependency only in the plan or only in the tracker, milestone, owner, a likely match, an issue with no unit, a unit with no issue, a unit label that names no unit) has a line saying the condition that makes it appear and a line saying how to settle it, which side to change and how (`SETTLE` in src/tracker/settle.ts). The Match step shows both under each group with entries, says plan versus tracker once (`PLAN_VS_TRACKER`), and a status row says how the mapping read the tracker's status. The tracker pack's rules carry the same lines as their `how`. The engine never touches the network: raw tracker exports are files, and `<instance>/tracker/` holds `inventory.json` (discovered), `mapping.yaml` (declared by the organization: phase as epic, initiative, fix version or label. unit as an issue type. dependency as a link type and direction. owner team as component, custom field or project. done-condition as a field. status by category or by name), `links.yaml` (confirmed unit -> issue matches, with who and when) and `reconcile.json`. The raw export is read from `--from`, else engine.yaml `tracker: { export: <dir> }`, else the directory discovery recorded in `inventory.json`. The last two are relative to the instance directory, so a copied instance names its export in engine.yaml, and an export that is not there is a `tracker` finding saying which path and what to set. Adapters implement `src/tracker/adapter.ts` (Jira today). Reconciliation is generic (`src/tracker/reconcile.ts`). its categories are findings of the `tracker` pack, and tracker state is shown beside each unit, never written into it. Types: `Tracker*` and `Bundle.tracker` in `src/types.ts`.

## CLI

- `bun plumb.ts build <instance-dir>`: compile, check, analyze, layout, write `build/<name>/bundle.json` and `index.html`. Exit 1 on error findings, but still write the outputs (the demo shows red).
- `bun plumb.ts check <instance-dir>`: findings to stdout, exit 1 on errors.
- `bun plumb.ts brief <instance-dir>`: what changed and what needs a person, as Markdown, read-only (src/core/brief-cli.ts): the status sentence and a row per milestone (shown, computed, first reason, override), the since-report line, open questions, proposed patches with verdicts, error findings, the tracker's counts and newest update, build warnings, and the frontier ranked by `unblocksTransitive`. It builds in memory and writes nothing.
- `bun plumb.ts impact <instance-dir> <patch-id>`: impact report as Markdown, opening with `## Verdict: <level> (...)`, its reasons, and the reject and revise lines.
- `bun plumb.ts plan <instance-dir>`: frontier, critical path, phase progress as Markdown.
- `bun plumb.ts premise <instance-dir> [claim-id]`: "if this is false" as Markdown. exit 1 on an unknown claim.
- `bun plumb.ts diff <instance-dir> --from <bundle.json | git ref> [--to ...] [--save] [--json]`: compare built bundles or this instance at a git ref. Generated JSON is the portable comparison format for imported designs.
- `bun plumb.ts vault <instance or portfolio> --out <dir> [--packaging] [--today YYYY-MM-DD]`: write a generated Obsidian vault and import human annotations as proposal notes.
- `bun plumb.ts package <out-dir> [--with-mcp]`: a verified standalone bundle (below).
- `bun plumb.ts report <instance-dir> [--presented]`: save a report snapshot. say what changed since the deck's baseline before it.

## Package

`plumb package <out-dir> [--with-mcp]` stages the standalone product: engine code, packs, templates, skill, docs, fictional examples, tests and fixtures. No workspace designs or pair importer ship. Build outputs, report snapshots, saved diffs, tracker measures, portfolio locks, editor litter and scrub lists are excluded. Fictional authored examples retain their scenario notes. The optional MCP server and its test ship only with `--with-mcp`; pure query tools always ship.

MANIFEST records each other file's SHA-256, size and relative path. A leak scan over every staged file, including MANIFEST, rejects home paths, real email addresses and configured scrub-list patterns. An absent scrub list is explicitly reported. A failed check writes no output. Output must be new or empty and outside the source tree.

## Skill

skill/plumb/SKILL.md routes to workflows for design and portfolio orientation, root estimates, slowdowns, exceptions, current-state confirmation, BAU refresh, notes, design patch drafting, patch review, progress, Jira reconciliation, decks and released editions. Every workflow declares commands, artifacts and a done condition. Root patches use portfolio impact. Agents never edit org.yaml or shipped seams.yaml for routine decisions. They never accept a patch, record risk acceptance or confirm a discovery without the user's words. Existing authorization continues to apply.

A command rehearsal can validate file shapes but cannot substitute for a model test. Record model availability, commands, outputs and every skill gap honestly.

## Schema 0.4 and shared composition

A design declares `schema: "0.4"`, a namespace, one root and optional exact pins. The root declares `kind: root` and brings namespaces shared and optionally org. Namespace shared holds systems, zones, parts, contracts, crossings, capabilities, seams, claims and manual-work vocabulary. Org holds teams, activities, slowdowns and exception lists. The team map is one role vocabulary for every rooted design. An organization layer and design-local teams at once are `core/one-home` errors.

A bare reference resolves own records, then shared records, then org in a team field. Canonical outside references use namespace:id. A kind-qualified form namespace:kind/id disambiguates fields that take several kinds. A design cannot depend directly on another design's records. Descriptive views, claim links and note targets may refer outside. Crossings and capabilities live in the shared layer and resolve where their design endpoints are composed. Missing designs are reported as outside scope rather than fabricated.

A portfolio selects its root and designs by relative path. Working composes latest files. Presenting selects each design's newest released edition, with a labelled latest fallback where none exists. Released designs use current progress, milestone status, notes, tracker data and current state. Accepted patches outside the frozen edition do not change that released design. The generated lock has separate working and presenting sections. It is evidence of resolution, not a hand-edited source of records.

Schema absent with no 0.4 fields is silently read as 0.3. An unsupported newer schema stops the build. A 0.4 feature without its schema reports a warning. Deprecated keys are read during the expand-and-contract window with warnings. Migration is idempotent, has a dry run and leaves generated files to the importer. Moved-id migration rewrites hand-written files from the shipped map.

The shared file's imported hash is checked by shared/file-intact. An organization changes shared records with root patches, not by rewriting published bytes. Root model hashes include explicit row owners and structural data but exclude leads and estimate notes. Build hashes include live state. A lone instance gets no new namespace, root, rule set or 0.4 bundle field. Its historical golden changes only engine.version and engine.built.

## Org estimates, decisions and workload

Every capacity and share has value, source, by, as_of and confidence. Capacity is a whole WIP limit of at least one. A share is from zero to one. Invalid required estimate fields prevent computation and produce org/estimate-valid errors. Source is person, agent, tracker or derived. Confidence is low, medium or high. An optional stated figure keeps the person's value beside a measurement. Historical input points and accepted root patches form history in natural patch order. Stale values and statements not made by the row owner stay labelled.

Root patches support team, activity, slowdown and exception records, plus shared design records. An estimate modify op replaces its complete estimate mapping. Exceptions are keyed by seam. Adding `{ seam, exceptions: [...] }` declares the org list. Modifying the seam sets its complete exceptions list. Removing the org record restores the shipped default. Empty lists decline defaults. Proposed patches are not applied. Only an explicit accepted decision changes the view. A root patch's impact must be evaluated in the portfolio because references, security and load span designs.

An activity has a team, type bau or stream, flow_item and share. Manual-work links join it to the shared catalog. A relief names a work unit or milestone and either retires the activity or reduces it to another sourced estimate. A unit's default flow_item is overridden in progress.yaml without editing the release. Missing classifications remain visible in work mix.

A slowdown records activity, what changes, share_during, from, until, risk.rises, accepted_by and accepted_at. Optional max_until and review_by are dates. A valid slowdown applies during its interval, ending at a date, a reached composed milestone or its maximum date. Missing acceptance prevents application. Overdue milestones and passed review dates are reported. A risk acceptance does not itself accept the containing patch.

Capacity analysis sums standing shares and simultaneous in-progress units across designs. Ownership divided among teams stays explicit. Unknown capacity remains unknown. A team over capacity on open work leading to any next milestone is an error. Portfolio impact shows how a root proposal changes that load and which designs it affects. It does not infer staffing or measured savings from an allowance.

## Seams and security

A crossing connects different homes and is declared whole in shared. It carries a shared contract or a non-empty no_contract reason as required by crossing validation. A module seam names its own crossings and carried contracts. Forbidden contracts remain forbidden. Shipped security floors are authoritative. A patch may raise relevance with security.raised but cannot rewrite or lower a floor. Signals provide a provisional floor only for records the shipped file did not hold.

Exceptions require contracts, accepted_by, until and why. The organization list replaces the shipped defaults for its seam. A valid exception changes only the seam rule's treatment. Design security packs still run over the composed graph and keep their severity. Checks also cover exact pin hashes, pin loops, stale working pins, cross-design capability cycles, shared-file integrity and cross-namespace references. Judged subjects remain auditable across composition.

## Current state in 0.4

current.yaml is a live overlay with parts keyed by own part id. Each may carry baseline, disposition, found, confirmed, add and replaced_by. Dispositions are new, retain, transition, replace and retire. Missing disposition remains undecided. Discovered records are shown immediately. A confirmation has a person's by and at, and cannot name an agent. A refused confirmation leaves the record discovered. A today-only add names a system this design places parts in. A design cannot record shared parts' current state. Its replacement can be a shared part.

Retirement is plan work with a fidelity move to the terminal level retired. That move is valid only for replace or retire dispositions. Replacement and retirement checks run across the composed plan. Ordering within a design uses milestone order. Across designs it uses target dates and reports no ordering inference when a date is missing.

## Root tracker measurement and portfolio output

A root tracker mapping declares kind org. Discover reads local exported responses. Draft-mapping keeps existing choices in mapping.yaml and writes a separate draft. Measure uses status history for days in doing, or a labelled lower confidence issue-count fallback. The measurement window ends at the explicit as-of date, export date or latest update in that order. It classifies activities, design work and unclassified time, retains coverage and confidence, and never calls a tracker service.

Discover compares with the previous inventory before writing. It reports created, changed or unchanged and lists added, removed and changed records. It distinguishes mapping vocabulary changes from usage counts and source metadata. Array order and JSON key order do not count as changes. A missing mapping or changed vocabulary calls for draft-mapping. A valid mapping can be reused when vocabulary is unchanged.

Measure writes tracker/measures/date.json. With --draft-patch it proposes every measured change in one root patch, preserving stated values. An identical pending refresh is reused. No changed values means no proposal. Optional --limits includes WIP limits when requested. The user accepts or rejects the entire refresh. Portfolio data shows measured gaps while it waits.

Portfolio output includes computed status, next milestones, dependency and capacity results, estimate histories, allowances, slowdowns, seam marks and exceptions, findings and design pages built in that composition. The page labels working or presenting and each resolved edition. Build writes outputs even with errors. Check, brief and impact are read only. Shared-root build writes root.json. Dev and publish support both portfolios and designs.

The roadmap renders undated milestones as an ordered strip with one tile per phase, status and open-unit count. Tiles retain plan order and wrap at narrow widths. Dated milestones stay on the month grid, including overdue targets. A design with both shows its dated row above its undated strip. A portfolio with only undated phases has no empty month grid.

## Obsidian vault output in 0.5

`bun plumb.ts vault <instance or portfolio> --out <dir> [--packaging] [--today YYYY-MM-DD]` builds a generated Obsidian vault. It uses the same compiled model, accepted patches, plan, live current state and findings as the site. Portfolio builds compose their shared root and designs through `runPortfolio`. They do not write a portfolio lock. A lone design retains its existing schema behavior. Schema failures stop output. Existing error findings exit 1 after output, as a site build does.

The engine version is 0.6.0. The design schema remains 0.4, and lone legacy instances retain their schema behavior.

The vault contains one Markdown note per part, relationship, contract, unit, milestone, team and finding. It includes a design index for every design and a portfolio index when the input is a portfolio. Shared and org records have one home. Relationships link endpoints and carried contracts. Contracts link producers and consumers. Units link changed parts, owner teams and milestones. Findings link their subjects. Indexes link their records. References without a generated home are rendered as unresolved or outside references in plain text. The generator emits wikilinks only for notes present in the output. It requires no Obsidian plugins.

Filenames use the record's readable name, preserving spaces, case and Unicode in NFC form. Path, control and wikilink characters are replaced with spaces; empty names, reserved device names, trailing dots and long names are made filesystem-safe. Names are capped at 180 UTF-8 bytes before suffixes. Contracts use their local declared name; relationships without a label use their local id. Collisions are compared after sanitization, Unicode normalization and case folding across every note kind and design. Only colliding names receive a parenthesized eight-character SHA-256 prefix of their full kind/id identity. The prefix grows if needed to avoid an existing natural name or another suffix. Allocation is deterministic and independent of input order. Every generated wikilink has explicit display text, `[[filename|Record name]]`, including links to indexes and collision-suffixed notes. Reserved characters in display text use HTML entities. A finding identity includes its rule, subject, message hash and occurrence so multiple findings on one subject remain distinct. An outside part whose design is absent has no editable source home and is described as outside the vault.

Every frontmatter mapping has string `id`, `kind`, `design`, `name` and `status`, list `aliases: [record name, qualified record id]`, list `owner_team`, and nullable date string `as_of`. Kinds are part, relationship, contract, unit, milestone, team, finding, design and portfolio. Scalar record fields stay typed top-level properties, including a unit's qualified `phase`, milestone `order`, relationship endpoints and optional flags. `record_kind` distinguishes the model's kind from the vault note kind. Strings stay strings, including dates and ids; numbers, booleans and null retain their types. Descriptions, checks and other prose appear in the body. The Record details section renders remaining structured fields, including attributes, unit element moves, requires and provides, as labeled nested Markdown lists. Frontmatter has no raw `attrs`, `record` or other nested mapping blobs. Unit status defaults to todo. Milestones retain computed status beside the effective status. Findings use severity as status. Parts without recorded current state use unrecorded, which does not imply confirmation.

Part frontmatter includes `state`, `baseline`, `disposition`, `refused` and `today_only`. The engine's compiled current-state verdict controls state. Discovery provenance is flattened into `found_by`, `found_agent`, `found_from`, `found_as_of` and `found_confidence`. Confirmation uses `confirmed_by` and `confirmed_at`, only as compiled by the engine. Missing provenance values are null. Refused agent confirmations remain discovered, have null confirmation properties and carry their refusal reason. The body visibly marks discovered-only and confirmed parts and includes the engine's provenance sentence. Current-state evidence is not inferred for relationships, contracts or other records without a current-state home.

Each note has a Human notes region delimited by exact marker lines `<!-- plumb:human:start -->` and `<!-- plumb:human:end -->`. The region is a pair of comment fences so ordinary Markdown annotations render in Obsidian. Its bytes survive regeneration. The generated shell includes everything outside the markers, including frontmatter and Engine notes. `.plumb-vault.json` format 1 records a shell hash and stable kind/id identity per filename. Existing filenames and identities are validated, including duplicate identities. Human regions are mapped by identity, allowing record renames, collision suffix changes and migration from the original id-based filenames. Obsolete records are identified by identity rather than filename. After preflight and leak checks, verified notes whose filenames change are moved through a temporary sibling folder before writing the new shells and manifest; this handles name swaps and case-only renames without deleting notes. Empty temporary folders are retained. Duplicate or damaged fences and shell edits are conflicts. All existing files are checked before any annotation is imported or vault output is rewritten. Missing generated notes, unmanaged files and obsolete records are reported and retained. The command refuses regeneration on these conflicts. Obsidian owns `.obsidian`, which is excluded from generated-file checks. The engine never deletes output files.

A non-empty human-region revision becomes an open person-authored note in the existing `notes.yaml` format. Its text identifies it as a proposal for review. The target uses element for a part and phase for a milestone. Team and index notes use team, design and portfolio targets. A design annotation goes to that design's notes file. Shared and org annotations go to their root's notes file. Portfolio index annotations and portfolio rule findings go to the portfolio's notes file. `sources` includes a vault identity and content hash. Proposal ids also derive from that content identity, making retries idempotent even after a page answer replaces the answer sources. Emptying a region does not erase prior notes. Editing a previously imported region creates another proposal note so the earlier proposal and any answer remain available. Existing source notes and answers render into Engine notes on the next generation. Import preserves unrelated notes and comments through `editNotesText` and the shared version-checked atomic file writer used by the local notes API. Unreadable source notes are refused. No annotation becomes an automatic record edit or accepted patch.

Generation sorts output and uses canonical serialization without build timestamps or source paths. Without `--today`, the build has no current date for relative checks. `--today` sets the build date explicitly. Import timestamps appear only in source notes and are part of the subsequent input state. Repeating the same build against unchanged source and annotations writes identical bytes, including the manifest.

`--packaging` reuses `leakCheck` from `src/dev/package.ts`, with strict email checking. It reads the package scrub list from `PLUMB_SCRUB_LIST` or the usual user configuration location. All generated bytes, the manifest, existing engine notes and preserved human annotations are scanned before output. The initial scan precedes source-note imports. Scrub-list patterns have no landscape exemption in a vault. All email addresses are refused, including documentation placeholders. Home paths on macOS, Linux and Windows and tilde home paths are refused. A missing scrub list is reported as unchecked names. A failure prints only filenames, line numbers and match kinds. It retains the prior vault. Existing application settings under `.obsidian` are scanned during packaging and preserved without changes.

## Premise reconciliation in 0.6

A premise is a claim with kind premise. Its falsifier is attrs.falsifier. Load and if_it_flips are attributes, and fallback is the claim's fallback. The shared premise register is normalized into the same model. Discovered evidence and person-confirmed evidence remain separate. The engine never writes reconciliation input or promotes found evidence.

### Cross-design settling work

A claim's attrs.tested_by accepts a unit id or a namespace:unit-id, in a string or list. An own-namespace id resolves locally. In a lone design, a foreign namespace is external, remains in the bundle and produces no error. Strategy says which design and unit settles it and says “not in this workspace” when absent. An absent unit contributes nothing to exposure. In composition, a present foreign unit contributes its actual status. Milestone orders from different designs are never ranked against each other. When settling work is foreign, exposure counts all open work in the premise's own design that rests on it and marks the settling designs as outsidePlanOrder. This also applies when local and foreign tests are mixed, since there is no shared order to select their earliest test. Strategy and the deck say it is settled in the named design, outside this design's plan order. Within one design exposure is unchanged. A missing unit in a present design is an error. An unknown namespace in a portfolio produces a warning naming the full reference.

### Read-only premise projection

`plumb premises <instance-or-root-or-portfolio> [--json]` builds in memory and writes nothing. A portfolio selects its listed designs plus the root register. An instance selects that design plus its register. A root alone selects its register. Programmatic root composition selects the explicitly supplied designs too. No sibling design discovery occurs. Exit is zero despite build findings, unless inputs cannot load.

Text has one block per premise grouped by design. JSON is one object with designs, premises, links, runs and debt. Premises have qualified id, design, statement, grade, falsifier, load, if_it_flips, fallback, rests_on, settling_units, hash, preview and every touching link. Preview is the additional reach through found steps, with tagged paths and the extra plan slice. Validation findings print on stderr in text and JSON modes, leaving stdout JSON valid. Shared ids use shared:id. Settling unit ids are qualified and include status when present in scope. Only kind premise enters this register projection. Other claim kinds retain existing impact behavior.

### Evidence file and validity

The sole home is premise-links.yaml beside team-map.yaml in the shared root directory. It is never part of seams.yaml or an edition. The file has links and runs lists. A link has a unique PL-<digits> id, qualified from and to premise ids, type depends-on, contradicts or duplicates, and found with by, at, reasoning and non-empty sources. From names the premise at risk. To names the premise it relies on. Optional confirmed has a person's by, at, falsifier_clause, moved_clause and pins with from and to hashes. Agent confirmation is invalid.

A premise hash is the first 12 lowercase hex digits of SHA-256 over normalized statement, a newline, and normalized falsifier. Each field independently collapses whitespace runs to one space and trims. Current hashes and status are computed in the bundle and never written to the source. A link is confirmed only when confirmed is present and both pins equal current hashes. It is stale if confirmed is present and either pin differs. Otherwise it is found. Stale dependencies behave as found.

Validation reports build findings and leaves other output buildable. Malformed input and link ids, duplicate ids, unresolved premises in a present namespace, self links, unknown types, incomplete discovery or confirmation fields, malformed pins, and invalid clauses are errors. A falsifier_clause must be a non-empty exact substring of the to premise's falsifier. A moved_clause must be a non-empty exact substring of the from premise's load, if_it_flips or fallback. Text is checked without whitespace normalization for clauses. A bad confirmation retains the link and found evidence with found status, reports its errors and never contributes confirmed impact. A link with neither endpoint namespace in scope is skipped silently. Exactly one absent endpoint namespace produces a warning and that link is skipped. Unknown top-level keys are warnings. A depends-on cycle is a warning naming its premise path.

Each run has id, by, at, designs, pairs_considered, pairs_skipped, rule and proposed. Counts are integers at least zero. Designs and proposed are string lists, with a non-empty designs list. Duplicate run ids are errors. A skipped-pair count produces a warning naming the run and its selection rule as its source. The skill records individual skipped pairs with reasons and sources and references that evidence from the rule. Every run has a record even when no links are proposed.

### Impact and review flags

The existing premiseImpact walk follows reverse rests_on edges and reverse depends-on links. A link A to B reaches A when B flips, then continues through the records resting on A and A's settling units. Each link traversal retains its link id and confirmed or found tag. Stale steps tag found. The seen set bounds cycles. Confirmed routes are exhausted before proposed routes so a found route cannot mask a confirmed one.

Default dependents, counts, plan slice, open work, Strategy counts, deck counts and the MCP premise answer count only routes with no found step. A preview contains the additional reach through at least one found step, with tagged link paths and the extra plan slice. Contradicts and duplicates never enter the walk. They produce warning findings labelled “review flag” naming both premises. Confirmation changes no impact for either type. Duplicates never merge premises.

### Bundle, pages, MCP and skill

A rooted design bundle, root bundle and portfolio data expose premiseLinks with links, runs and debt. Links retain discovery and confirmation evidence, computed status, hashes and changed sides. Debt has found, stale, flags and last_run. Found and stale count depends-on links only. Flags counts contradicts and duplicates regardless of status. The counts do not overlap. Last_run is the final valid run in file order, or null. The Reconciliation section is hidden when premise-links.yaml is absent and shown when the file exists, even if empty. Legacy lone bundles retain their historical shape.

Strategy details show incoming and outgoing links, status and confirmation clauses or proposal reasoning. Reconciliation lists found links awaiting a person, stale links with which side changed, review flags and the sentence “The last run considered N pairs across <designs> and skipped M: <rule>.” Page labels use plain text. Ids stay in detail cards. Portfolio shows one debt sentence. Offline files open no connection. The read-only MCP premise tool includes touching links and the would-cascade preview. It adds no writing tool.

The reconcile-premises workflow declares scope, inputs and done condition immediately. It runs the JSON projection, considers all cross-design pairs including shared premises or records exact selection and skipped-pair evidence, proposes found links quoting both relevant clauses, and records one run. It groups proposals by their possible cascades. Only a person's explicit word for one link authorizes confirmed with the clauses that person picked and current projection pins. It never bulk-confirms. A rebuild shows confirmed impact and proposed reach separately. These instructions apply equally to Opus 5.5 and Sonnet 5 without harness defaults.
