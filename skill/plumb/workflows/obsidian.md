# Open a design in Obsidian and write a vault note

Use this workflow when asked to open the design in Obsidian or write a note in the vault. The vault is generated output. The checked engine files remain the source of truth.

Read the requested design's engine.yaml or the portfolio's portfolio.yaml to locate the input. Run `bun plumb.ts vault <input> --out <vault-folder>`. Use an existing generated folder when the user wants its annotations preserved. Use `--packaging` when the vault will be shared or moved to another machine. It scans preserved annotations too. Report when scrub-list names were not checked. Use a supplied `--today YYYY-MM-DD` for date-relative status. Without it, time-relative checks have no current date.

In Obsidian, choose Open folder as vault and select that folder. Open its design or portfolio index. Notes use readable record names, with short suffixes only for filename collisions. Generated wikilinks always display the record name. Aliases contain the name and qualified id for search and link suggestions. The graph, backlinks, search and Bases work with the generated Markdown and YAML properties. Filter by kind, design, status, state, owner_team or a unit's phase. Discovery properties use found_by, found_agent, found_from, found_as_of and found_confidence; confirmation uses confirmed_by and confirmed_at. Structured attributes and other record details are readable in the body. Discovered-only parts are explicitly marked and must not be described as confirmed.

To write a note, locate the generated record by its name or id alias and verify its id and kind in frontmatter. Write the user's annotation between `<!-- plumb:human:start -->` and `<!-- plumb:human:end -->` under Human notes. Preserve both marker lines exactly. Do not edit frontmatter or the generated body. Ordinary Markdown is allowed inside the region. Run the same vault command again. If a source name changes, the manifest carries the human text by record identity and the generator moves the note to its new readable filename, including when upgrading an original id-based vault. Do not rename generated files by hand.

Regeneration keeps the human region and imports each non-empty revision once as an open proposal in the existing notes.yaml path. Design records use their design's notes file. Shared and org records use the root's notes file. The portfolio index and portfolio rule findings use the portfolio's notes file. Emptying the region does not delete an existing engine note. Editing the region again creates a new proposal, preserving prior discussion. Read the imported note and use [answer-a-note.md](answer-a-note.md) to answer it. When the user requests a design proposal, use [draft-a-patch.md](draft-a-patch.md). Record changes and confirmations still require their existing decision workflows. Vault text never grants acceptance or confirmation.

Answers written through the existing note path appear under Engine notes on regeneration. Leave that section generated. If regeneration reports an edit outside a human region, a missing note or a record that no longer generates, report the filename and retain the affected file. Preserve annotations before restoring the generated shell or building a fresh vault folder. Never silently merge those edits or delete old files. Leave .obsidian application settings alone. Packaging scans those settings too and refuses output if they contain a leak. Share a fresh generated folder after a successful packaging check.

Report the output folder, note count, imported proposal count, findings and any conflict or leak-check failure. An exit of 1 can mean the vault was written with existing error findings. Read the command output to distinguish that from a refused write.
